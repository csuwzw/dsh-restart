# dsh-restart 1.0.2 验收记录

本文记录 1.0.2 的每一项能力及其取证方式，不含推测。基线为 DeepSeek Harness 桌面版内核
`0.2.0-rc.2`，Windows 11，profile 名 `desktop`。

本版只改一件事：**重启成功判据从「等旧端口」改为「按新实例判定」**。因此验收的重点是
「新判据在真实进程树上给出正确结果」，而不是重跑一遍 1.0.0 的全部能力。

## 一、判据为什么必须改

1.0.0 的判据（`restart.ps1` 第 5 步）是等**旧实例**的端口 `$Port` 重新进入 Listen：

```powershell
$listening = $false
$verifyDeadline = $launchedAt.AddSeconds(30)
while ((Get-Date) -lt $verifyDeadline) {
	if (@(Get-NetTCPConnection -LocalPort $Port -State Listen -ErrorAction SilentlyContinue).Count -gt 0) { $listening = $true; break }
	Start-Sleep -Milliseconds 500
}
```

`$Port` 来自宿主端 `index.js`：

```js
const port = req.socket?.localPort
```

而桌面版 Host 固定以 `--port 0` 启动，端口每次由系统分配（`dsh-desktop-host/lib/index.js`）：

```js
args: ["--no-open", "--host", "127.0.0.1", "--port", "0"]
```

新实例几乎不可能拿到与旧实例相同的端口，所以这个判据**结构上就是错的**——重启成功它也会
报 `listening=False`。

`$DSH_HOME/logs/dsh-restart-plugin.log` 的真实记录：

| --- | --- | --- |

| 2026-10-17 03:39:06 | 19387 | `listening=True after 5s` |

| 2026-10-18 21:10:23 | 58311 | `listening=False after 31s` |
| 2026-10-18 21:14:08 | 54467 | `listening=False after 30s` |

复用了刚释放的旧端口（`54348` 等 TIME_WAIT 端口尚在回收池里）。

## 二、新判据的真机取证

新逻辑（`restart.ps1` 第 5 步，与 PR #1 一致）：

```powershell
# 5) 事后确认：等这次拉起的新实例把 Host 跑起来，只写日志、不重试。
#    桌面版固定以 --port 0 启动（Web 端口由系统分配），新实例的端口与旧实例不同，
#    所以这里不按 $Port 判断：先找新主进程，再找它下面跑 desktop-host 的 Host 子进程，
#    看它有没有在监听。Host 与 runner 的进程名相同，靠命令行区分。
$exeName = Split-Path -Leaf $Exe
$started = @()
$newMain = $null
$newHost = $null
$listenPorts = @()
$verifyDeadline = $launchedAt.AddSeconds(30)
while ((Get-Date) -lt $verifyDeadline) {
	$started = @(Get-CimInstance Win32_Process -Filter "Name='$($exeName.Replace("'", "''"))'" -ErrorAction SilentlyContinue |
		Where-Object { $_.CreationDate -ge $launchedAt.AddSeconds(-2) })
	$ids = @($started.ProcessId)
	# 新进程树里唯一「父进程不在树内」的那个，就是这次拉起的主进程。
	$newMain = $started | Where-Object { $ids -notcontains $_.ParentProcessId } |
		Sort-Object CreationDate -Descending | Select-Object -First 1
	if ($newMain -ne $null) {
		$newHost = $started | Where-Object {
			$_.ParentProcessId -eq $newMain.ProcessId -and $_.CommandLine -match 'dsh-desktop-host[\\/]lib[\\/]index\.js'
		} | Select-Object -First 1
	}
	if ($newHost -ne $null) {
		$listenPorts = @(Get-NetTCPConnection -OwningProcess $newHost.ProcessId -State Listen -ErrorAction SilentlyContinue |
			ForEach-Object { $_.LocalPort })
		if ($listenPorts.Count -gt 0) { break }
	}
	Start-Sleep -Milliseconds 500
}
```

把上面这段原样抽出来，对当时的真实进程树跑一遍（不重启应用，只跑判据）：

| 项目 | 期望（真值） | 实际输出 |
| --- | --- | --- |
| 主进程 | `65108` | `main=65108` ✓ |
| Host 子进程 | `66888`（命令行含 `dsh-desktop-host\lib\index.js`） | `host=66888` ✓ |
| 监听端口 | GUI 所在的 `63845` | `listening=[63845]` ✓ |

按判据的格式渲染出来的日志行是（`after` 秒数为本次手工跑时填的值）：

```
verify: main=65108 host=66888 listening=[63845] after 9s
```

**这次是算法级取证，不是流程级取证**：没有真的按按钮重启应用，而是把脚本第 5 步原样抽出来、
对着当时那棵真实进程树跑了一遍。三项（主进程 / Host 子进程 / 监听端口）都对上了真值，
说明判据的选靶逻辑正确。真实重启时这段代码会拿到同一棵形状的树。

> **本节之后有过一次真实的端到端运行**（二之二节）。那次跑出来的结论是：**「端口非空」这一项
> 对上了也只是巧合，它本身不可靠。** 所以上表「监听端口 ✓」只证明选靶逻辑对，不构成判据依据；
> 最终判据看的是 Host 进程是否存在，端口降为附加信息。

旧判据为何不能作为对照，值得说明：本次没有重启，新旧「实例」其实就是同一个进程，所以把
`oldPid` 端口填成当前 GUI 端口时旧判据也会报 `True`——**这种对照没有信息量**。旧判据的失效
是靠第一节那份真实日志证明的：10-18 起端口随机化后它连续报 `False`，而 `oldPid` 链条证明
进程每次都在正常换代。两者的区别在于，旧判据的正确性依赖「新实例端口 == 旧实例端口」这个
偶然条件，而新判据认的是新实例的 Host 进程是否存活，与端口号无关。

进程树真值（`Get-CimInstance Win32_Process`）：

```
pid=65108  ppid=64280  "C:\D\software\DeepSeek Harness\DeepSeek Harness.exe"
pid=62812  ppid=65108  --type=gpu-process ...
pid=64332  ppid=65108  --type=utility --utility-sub-type=network.mojom.NetworkService ...
pid=61588  ppid=65108  --type=renderer ...
pid=66888  ppid=65108  --expose-internals "...\dsh-desktop-host\lib\index.js" ...
pid=52512  ppid=66888  "...\dsh-subprocess-local\lib\runner.js"
```

`66888` 与 `52512` 进程名相同（都是 `DeepSeek Harness.exe`），只有命令行能区分——这就是判据
必须匹配 `dsh-desktop-host[\\/]lib[\\/]index\.js` 而不是只匹配进程名的原因。

## 二之二、真实端到端运行：端口非空当判据是错的（本版最重要的一次翻案）

上面那套「端口非空即成功」的判据在**算法级**测试里全绿，但真按一次按钮就露了底。

2026-10-19 06:22 的真实运行日志（维护者点的按钮，非模拟）：

```
2026-10-19 06:22:46.595  armed: oldPid=65108 port=63845 exe=C:\D\software\DeepSeek Harness\DeepSeek Harness.exe
2026-10-19 06:22:47.112  taskkill /PID 65108 /T /F -> exit=0
2026-10-19 06:22:47.975  launched: C:\D\software\DeepSeek Harness\DeepSeek Harness.exe (old alive=False)
2026-10-19 06:23:19.100  verify: main=61696 host=60140 listening=[] after 31s
```

新格式生效了、**两个 pid 都选对了**（`61696` 是拉起的主进程，`60140` 是它下面跑
`dsh-desktop-host\lib\index.js` 的 Host），但 `listening=[]` 空——按当时的成功条件就是 `False`。

**可是重启确实成功了**：那一刻之后 GUI 一直在 `http://127.0.0.1:52368` 正常服务，
`60140` 的启动时刻是 06:22:48，从那时起就没死过。

### 根因：端口枚举在这个环境里间歇性失效

对同一个 pid（`60140`）连续尝试五次，交替使用两种通道：

| 尝试 | 进程存活判据 | `netstat -ano` 的 LISTENING 行 | `Get-NetTCPConnection -OwningProcess` |
| --- | --- | --- | --- |
| 1 | ✓ alive | 1 行 | 抛异常 |
| 2 | ✓ alive | **0 行** | 抛异常 |
| 3 | ✓ alive | 1 行 | 1 行 |
| 4 | ✓ alive | **0 行** | 抛异常 |
| 5 | ✓ alive | 1 行 | 1 行 |

- 进程存活判据：**5/5 全对**。
- `netstat`：五次里两次返回 0 行（此时其它探测能拿到 `[52368]`，说明端口是真的在听）。
- `Get-NetTCPConnection -OwningProcess`：五次里三次抛
  `No matching MSFT_NetTCPConnection objects found ... WHERE ((State = 2)) AND ((OwningProcess = ...))`。
  同一个调用在别的上下文里又能返回，还会冒出**并不存在的端口** `3082`（单独用
  `-LocalPort 3082 -State Listen` 查它，抛「找不到任何匹配的对象」——自相矛盾）。

也就是说：`listening=[]` **不代表重启失败，只代表这一次枚举没读到**。把端口非空当成功条件是
把判据建在了不可靠的地基上。

### 修正

`restart.ps1` 第 5 步改为 **`verdict = hostPid > 0 ? ok : fail`**，端口只作附加信息：

```powershell
$verdict = if ($hostPid -gt 0) { 'ok' } else { 'fail' }
Write-Log ("verify: main={0} host={1} listening=[{2}] verdict={3} after {4}s" -f $mainPid, $hostPid, ($listenPorts -join ','), $verdict, [int]((Get-Date) - $launchedAt).TotalSeconds)
```

端口仍然两条通道都试、结果合并去重，但**读不到就留空，不影响判定**。改完后对当时那棵真实
进程树复跑，输出为：

```
verify: main=61696 host=60140 listening=[] verdict=ok after 0s
```

`listening=[]` 保留原样（如实反映枚举失败），判定为 `ok`——这才是正确结论。

**这条是本版最该记住的教训**：算法级验证通过不等于流程级验证通过。判据依赖的任何系统 API，
都要在它**真实的调用上下文**里连续跑多次看稳定性，而不是跑一次拿到正确值就算数。

## 三、方法论踩坑：验证进程/网络 API 必须跳出沙箱

本条是本次验收最花时间的地方，记下来免得下次重踩。

在**受限上下文**里查端口，`Get-NetTCPConnection` 会给出与事实相反的结果：

| 查询方式 | 沙箱内（本会话） | 沙箱外（WMI 创建的同权限进程） |
| --- | --- | --- |
| `Get-NetTCPConnection -OwningProcess 66888 -State Listen` | 抛 `No matching MSFT_NetTCPConnection objects found ... WHERE ((State = 2)) AND ((OwningProcess = 66888))` | 1 条 `[63845]` ✓ |
| `Get-NetTCPConnection -LocalPort 63845 -State Listen` | 同样抛异常 | 1 条 ✓ |
| `netstat -ano \| findstr :63845 \| findstr LISTENING` | `(none)` | `TCP 127.0.0.1:63845 ... LISTENING 66888` ✓ |
| `.NET GetActiveTcpListeners()` | 不含 63845 | — |

与此同时 `Invoke-WebRequest http://127.0.0.1:63845/` 返回 **401**（有响应），证明端口**确实**在监听。

也就是说：沙箱内至少有三类 API 会对本用户自己的进程给出假阴性。若照沙箱内的结果下结论，
会误判「新判据也有 bug」，进而改坏一个本来正确的修复。

取证方式：用 `Win32_Process.Create` 起一个同用户、同权限的进程来跑探针和判据——

```powershell
Invoke-CimMethod -ClassName Win32_Process -MethodName Create `
  -Arguments @{ CommandLine = "powershell.exe -NoProfile -ExecutionPolicy Bypass -WindowStyle Hidden -File <探针>" }
```

（这同时也验证了判据依赖的 `Get-CimInstance Win32_Process` 在真实调用环境里工作正常。）

## 六、发布渠道

`v1.0.2` 的 git tag 指向本次提交，用 `refs/tags/v1.0.2` 安装即可拿到修复版。`v1.0.1` 的 tag
不可变，仍指向旧代码——只影响「按 1.0.1 文档里的命令装 tag」的人，升级到 `v1.0.2` 即解决。

**`v1.0.2` 这个 tag 被追加修正过一次（版本号刻意不变）。** 第一版 v1.0.2（把「端口非空」当
成功条件的那版）发布后，真机实测证伪了它的判据，于是把修复并入同一个版本号，用
`PATCH /repos/.../git/refs/tags/v1.0.2 {"sha":..., "force":true}` 把 tag 强制移到修正提交。
理由是：这次修的仍是 1.0.2 的功能缺陷本身，发 1.0.3 反而会让已装第一版 1.0.2 的人以为自己是
最新的。代价是 tag 不再不可变，所以在此如实记录。

对已经装过第一版 v1.0.2 的人，pnpm 有两道缓存会挡住同 URL 的内容变化：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 装完 `restart.ps1` 仍是旧的（没有 `verdict=`） | 内容寻址存储里已有同 URL 的旧包 | `pnpm store prune` 后重装，或直接删 `node_modules/dsh-restart` 再装 |
| 报 `ERR_PNPM_TARBALL_INTEGRITY` | 该项目的 `pnpm-lock.yaml` 锁了旧 tarball 的 `integrity` | 加 `--update-checksums`，或删掉 lockfile 里该条目 |

两条都已实测：把 lockfile 里的 `integrity` 改成假值后 `pnpm install --frozen-lockfile` 报
`[ERR_PNPM_TARBALL_INTEGRITY] Got unexpected checksum for "https://codeload.github.com/csuwzw/dsh-restart/tar.gz/refs/tags/v1.0.2"`，
并明确拒绝静默覆盖锁定的 integrity。**新装（两道缓存都空）不受影响**——用一个空目录实装过
`refs/tags/v1.0.2`，落到 117 行含 `verdict=` 的修复版。

## 七、未验证与已知边界

- **仅 Windows。** 未在 macOS / Linux 上测试，脚本依赖的 WMI、`conhost.exe`、`taskkill`
  在那两个平台上都不存在。
- **端到端重启实测做过一次，但只覆盖到「重启成功」这一路径。** 2026-10-19 06:23 维护者按过
  一次按钮，产生了真实的 `verify: main=61696 host=60140 listening=[]`——pid 选靶正确、重启
  成功，但端口枚举返回空，正是这次运行推翻了第一版的判据（见二之二节）。**未覆盖**的是
  「新实例启动失败」的路径：脚本在这种情况下应写 `verdict=fail`，但没有制造过该场景来验证。
- **判据对「新实例端口=旧实例端口」这种巧合不敏感。** 它认的是新实例的 Host 进程是否存活，
  与端口号无关，所以同端口不会造成误判——这正是它优于旧判据的地方。
- **`verdict=ok` 不保证 GUI 已能打开页面。** 从 Host 进程启动到真正 bind 端口之间还有初始化
  阶段，本版不探测 HTTP 可用性。
- **未测过新实例启动超过 30 秒的情况。** 超时后脚本只写日志、不重试（有意不做重试：旧实例已被
  终止时盲目重试会造出重复实例）。
- **未测过非默认 profile 名。** 参考实机为 `desktop`。
- **客户端产物改动需重启才生效。** 本 profile 未启用 `@deepseek-ai/dsh-client-hmr`。
