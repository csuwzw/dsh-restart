# dsh-restart 1.0.0 验收记录

本文记录 1.0.0 的每一项能力及其取证方式，不含推测。基线为 DeepSeek Harness 桌面版内核
`0.2.0-rc.2`，Windows 11，profile 名 `desktop`。

## 一、前置调查：桌面版确实没有可用的重启入口

在写代码之前，逐条确认了「更短的路都不通」，避免实现一个多余的东西。

| 候选通路 | 结论 | 取证 |
| --- | --- | --- |
| 应用菜单里的「重启应用与 Host」 | 生产版不存在 | `main.js` 的 `applicationItems()` 把该条目放在 `development ? [...] : []` 分支内 |
| 托盘菜单 | 只有打开/退出 | `DesktopTray.relabel()` 的模板固定两项 |
| 渲染进程 API | 无 quit/restart 成员 | preload 的 `dshDesktop` 只暴露 protocolVersion / browser / deviceInfo / keyboard / shortcuts / updates |
| 配置管理器 | 只提示手动重启 | 全库 grep 无 relaunch/restart 实现，只有 `report.restartRequired` 一类文案 |
| 发关闭消息 | 无效 | 主窗口 `close` 事件被 `preventDefault()` 改为隐藏到托盘 |

因此必须自己开一条通路。这也解释了插件存在的必要性——不是重复造轮子。

## 二、进程与 job object 隔离

问题：从插件里普通 spawn 出来的进程会与 Host 同处一个 job object，旧实例一退出就被连带带走，
拉不起新实例。

实测对照：

| 启动方式 | 新进程的父链 | 是否在 job 内 |
| --- | --- | --- |
| `child_process.spawn`（detached） | `…DeepSeek Harness.exe → Host → Electron` | **是**，随旧实例一起被杀 |
| `Win32_Process.Create`（WMI） | `WmiPrvSE.exe → svchost.exe → services.exe → wininit.exe` | **否**（`IsProcessInJob` 返回 FREE） |

WMI 进程同时满足启动 GUI 程序的条件：`sessionId = 1`（与 explorer 相同）、
`[Environment]::UserInteractive = true`、`user = <当前用户>`。用记事本做了前置验证——WMI 创建的
`notepad.exe` 窗口正常显示，`MainWindowTitle` 可读。

## 三、控制台窗口：三种启动方式的对照

问题：默认终端为 Windows Terminal 时，它忽略 PowerShell 的 `-WindowStyle Hidden`，脚本跑在可见
窗口里；新实例继承该控制台后窗口被日志一直占着，手动关掉还会连带杀掉新实例。

用 `EnumWindows` + `IsWindowVisible` + `GetClassNameW` 枚举控制台类窗口（`CASCADIA_HOSTING_WINDOW_CLASS`
/ `ConsoleWindowClass` / `PseudoConsoleWindow`），从干净基线（0 个）开始，每秒采样：

| 启动方式 | 脚本存活期内观察到的控制台窗口 |
| --- | --- |
| WMI → `powershell.exe -File restart.ps1` | **2 个**（`CASCADIA_HOSTING_WINDOW_CLASS` + `PseudoConsoleWindow`），全程 22 秒都在 |
| WMI → `wscript.exe //B //Nologo run.vbs`（VBS 内 `sh.Run cmd, 0, False`） | **0 个** |
| WMI → `conhost.exe --headless powershell.exe -File restart.ps1` | **0 个** |

选 `conhost --headless` 而非 VBS：不需要额外落一个 `.vbs` 文件，一条命令行搞定。

**踩坑记录**：第一次探针得出「四种模式都无新窗口」是假阴性——观察时机在脚本退出之后，而窗口只
存在于脚本存活期；且 Windows Terminal 会把新控制台开成已有窗口的标签页。改为「脚本存活期内持续
采样」后才得到上表。

## 四、端到端重启

真实运行记录（`$DSH_HOME/logs/dsh-restart-plugin.log`）：

```
2026-10-17 02:27:59.155  armed: oldPid=39848 port=19387 exe=C:\D\software\DeepSeek Harness\DeepSeek Harness.exe
2026-10-17 02:27:59.470  taskkill /PID 39848 /T /F -> exit=0
2026-10-17 02:28:00.332  launched: C:\D\software\DeepSeek Harness\DeepSeek Harness.exe (old alive=False)
2026-10-17 02:28:09.738  verify: port 19387 listening=True after 9s
```

四步齐全，`listening=True`。**9 秒恢复**。

`verify` 判据的选型：最初数 `DeepSeek Harness.exe` 进程，但 `@deepseek-ai/dsh-subprocess-local`
的 runner 子进程同名，干跑时误报 `count=2`。改为等端口监听——端口在听即 Host 已起来，与进程名
无关。

> **更正（2026-10-19，本文件的原始记录一字未改）。** 上面第四行的 `listening=True` 是当时的
> 真实输出，但这个判据本身是错的：它等的是**旧实例**的端口 `$Port`，而桌面版 Host 固定以
> `--port 0` 启动、端口由系统分配，新实例几乎不可能拿到同一个端口。此后的实测印证了这一点——
> 2026-10-18 起端口变为随机的 5xxxx 后，`listening=False after 30s` 反复出现，而逐次核对
> `oldPid` 链条（46676 → 49372 → 50340 → 50444 → 57124，每次的下一个 `oldPid` 就是上一次拉起
> 的新实例 pid）证明**每次重启都真的成功了**，`False` 是误报；10-19 04:14 那次偶然报出
> `port=51847 listening=True`，只是新实例复用了刚释放的旧端口。
>
> 判据已改为：先找这次拉起的主进程，再找它下面跑 `dsh-desktop-host/lib/index.js` 的 Host 子进程，
> 看它有没有在监听；日志格式随之变为 `verify: main=<pid> host=<pid> listening=[<port>,...] verdict=<ok|fail>`。
> 其中 `verdict` 看的是 Host 进程是否起来，端口只是附加信息——1.0.2 首版把「端口非空」当成功
> 条件，结果出现「重启真的成功了、日志却报 `listening=[]`」的假阴性，已修正。
> Host 与 runner 进程名相同，只能靠命令行区分。

## 五、路由与信任围栏

用桩 ctx + 真 http server 驱动路由（`POST /api/dsh-restart/restart`）：

| 请求 | 结果 |
| --- | --- |
| `GET` | 405 `method-not-allowed` |
| `POST` 但无自定义动作头 | 403 `forbidden-action` |
| `POST` 但 `content-type` 不对 | 403 `forbidden-action` |
| `POST` 正确 | 200 `{ ok: true, oldPid, exe, port }` |

最后一项的 `port` 是桩服务器实际监听的随机端口（58670），证明端口取自 `req.socket.localPort`
而非硬编码。

## 六、客户端产物离线自测

`node client.test.cjs client.js`，25 项检查全部通过（假 DOM，不需要浏览器、不出网）：

- 模块注册 id 正确、`apply` 是函数、`inject` 为空数组
- 菜单条未就绪时不报错，并挂上 MutationObserver
- 菜单条就绪后自动补挂按钮，`count=1`

- 中文界面取中文文案、切英文取英文、切回中文恢复

- 第二次点击才发出一次请求

## 七、未验证与已知边界

诚实列出本版**没有**做到的部分：

- **仅 Windows。** 未在 macOS / Linux 上测试，脚本依赖的 WMI、`conhost.exe`、`taskkill` 在
  那两个平台上都不存在。宿主端与浏览器端本身不含平台分支，但没有脚本就没有重启能力。
- **未测过 webServer 端口配成 0 的部署。** 端口取自 `req.socket.localPort` 的推理链已由桩服务
  验证（随机端口 58670 被正确取到）。当时认为「真实桌面版始终使用固定端口」故未在实机上跑——
  **该判断是错的**：桌面版 Host 固定以 `--port 0` 启动，端口一直由系统分配（见第四条的更正），
  所以这一形态其实每天都在跑。
- **未测过非默认 profile 名。** 参考实机为 `desktop`。插件本身不感知 profile 名（`process.ppid`
  与 `process.execPath` 与 profile 无关），但未在其它 profile 上实测。
- **未做重启失败自动重试。** 脚本只记录结果。旧实例已被终止的情况下盲目重试会造出重复实例，
  因此有意不做。
- **客户端产物改动需重启才生效。** 本 profile 未启用 `@deepseek-ai/dsh-client-hmr`，刷新页面
  拿不到新版。
- **图标为手工绘制的 SVG**，未做多尺寸栅格化，仅在 README 与 GitHub 页面上使用。

## 八、卸载验证

移除 `dsh.profile.bundles` 中的 `dsh-restart`、移除 `dependencies` 中的条目、删除
`node_modules/dsh-restart/` 后：

- profile 的 `cordis.patch.yml` / `cordis.yml` 无残留（插件不改写这两个文件，只声明自己的 patch 层）
- 无注册表写入、无服务、无计划任务（脚本全程只调用 `taskkill`、`Get-NetTCPConnection`、
  `Start-Process`）
- 日志文件 `$DSH_HOME/logs/dsh-restart-plugin.log` 为纯文本，可直接删除
